# 🚧 My Project Journey – Intelligent Conveyor Belt Monitoring & Prediction System

## Day 1 – Understanding and Planning

On the first day, I took complete responsibility for the **software development** of our project. Before starting the actual development, I wanted to understand how the hardware and software would communicate with each other.

My first focus was understanding **how the ESP32 would transmit sensor data to the software**. I studied how the sensor values could be collected and transferred to the backend, and how the software would handle those values after receiving them.

I planned the data flow as:

**ESP32 + Sensors → Flask Backend → ML Model → Database → Dashboard**

The sensor data would contain numerical values such as vibration, temperature, current, speed, tension, and other parameters. My teammate was responsible for training the Random Forest model using these sensor values, while another part of the system would use YOLO for camera-based belt-damage detection.

I then focused on how the **database should be established**. I decided to use SQL because it was simple, lightweight, and easy to implement in the software. I planned to store sensor readings, ML predictions, alerts, and inspection results so that the data could be used again for future analysis.

I also planned the overall architecture of the software, including the Flask backend, ML models, SQLite database, React frontend, and the digital twin.

**Day 1 was completely about planning and understanding the system.** I didn't implement anything yet, but by the end of the day I had a clear idea of how the different parts of the project would work together.

---

## Day 2 – Building the Foundation

On Day 2, I started turning the plan into an actual system.

I began with the **database**. I created the required tables and columns to store the different types of data that would be generated by the system, especially the numerical sensor readings and the results produced by the ML models.

By the afternoon, I started establishing the **backend**. I set up Flask and began creating the required API endpoints. This gave me the foundation through which the frontend, database, and ML components could eventually communicate.

After working on the backend, I moved to the **frontend**. I created five main pages:

- Dashboard
- Conveyor Monitoring
- Joint Health
- Vision AI
- Alerts

At this stage, I didn't connect the frontend to the ML models or database because I was waiting for the trained ML models from my teammates.

By the end of the day, I felt calm because the basic structure of the software was taking shape. My main thought was about **how I would connect the ML models to the backend once I received them**.

---

## Day 3 – Working with YOLO

Day 3 was when I started working more directly with the AI side of the project.

By the evening, I received a **partially trained YOLO model** from my teammate. My goal was to make it capable of recognizing belt tears.

I first tested the model with an image containing multiple tears. However, the model detected only **one tear even though the image contained several tears**.

This showed me that the model still needed improvement.

I continued training and testing the model, experimenting with different **confidence settings**. I kept working on it until night, repeatedly checking whether the model was detecting the tears correctly.

Eventually, I achieved a much better result. The YOLO model was able to detect **multiple tears** in an image.

I then tested it with **video footage**, and the model was also able to detect the tears in the video.

This was an important milestone for me because I had moved from simply having a model to actually getting useful detection results from it.

I didn't work on anything else that day after getting the YOLO model working.

---

## Day 4 – Integrating Vision AI

On Day 4, I started integrating the **YOLO model into the backend**.

At the same time, the hardware prototype was not ready, so I needed a way to continue developing and testing the software without waiting for the physical sensors.

I established a system where the **sensor values would continuously change every two seconds**. This allowed me to simulate the kind of changing data that I expected to receive from the hardware.

For the YOLO side, I had initially prepared around **10 fabricated images** myself. However, after looking at the system, I felt that depending only on those fabricated images would not be satisfying for the final demonstration.

So I changed my approach.

Instead of limiting the Vision AI page to those predefined images, I created an **image upload option**. This allowed a user to upload an image of a belt and receive a live detection result from the YOLO model.

I tested the image-upload system with different belt images, and the model correctly detected the tears.

This made the Vision AI section much more flexible and closer to how an actual inspection system could work.

---

## Day 5 – Preparing the Random Forest Model

Day 5 started with me waiting for the **Random Forest model** from my teammate.

There wasn't much I could work on while waiting for the model because an important part of the system depended on it.

By around noon, I received the Random Forest model and immediately started testing it.

The first problem I noticed was that the model had been trained using a **set of fabricated sensor values**. Although the model could produce results, this wasn't ideal for my planned system because the actual sensor values would continuously change.

I wanted the model to work with continuously changing values rather than only a fixed set of values.

So I started training the ML model again with this requirement in mind. I worked on making it suitable for analyzing changing sensor data.

By the end of the day, I had trained the model and planned how I would integrate it with my backend. However, I hadn't actually connected it to the backend yet.

---

## Day 6 – Bringing Everything Together

Day 6 was one of the most important development days for me.

I started connecting the **Random Forest model to the Flask backend** and then connected the results with the database.

During the integration, I encountered some bugs. Instead of stopping there, I worked through the problems, identified the issues, and fixed them.

After fixing the bugs, the complete flow started working:

**Changing Sensor Values → Random Forest → Flask Backend → Database → Frontend**

Once I got the ML results working, I focused on improving the **frontend organization and design**.

I wanted the user to immediately understand whether the **belt or a belt joint was in a correct condition or was damaged**. I didn't want the dashboard to simply show a collection of numbers.

I also added a small **digital twin representation of a single conveyor**, based on the conveyor prototype planned by our hardware team.

Another important part I wanted the user to see was the **history of the belt and joint condition**, so the system could provide information beyond just the current status.

After organizing the pages and displaying the required information, I tested the frontend with the actual ML results and sensor data.

The results were good.

By the end of Day 6, I had successfully brought together the major software components I had been working on throughout the week.

---

## Day 7 – Completing the Journey

Day 7 was relatively simple compared with the previous development days.

After completing the software, I pushed the **entire project to GitHub**.

I didn't make any additional changes or major modifications that day. The main purpose was to publish the work I had developed throughout the previous days.

Seeing the complete project on GitHub felt good because I could finally look at it as a complete system rather than separate pieces.

I had managed to handle the **frontend, backend, database, and ML integration** and bring them together into one working website.

---

# Final Reflection

Looking back at the journey, the biggest thing I learned was not just a particular programming language or technology.

I learned that **I can handle the entire development process on my own**.

I started with almost nothing implemented. I first had to understand how the hardware would communicate with the software, then plan the database, establish the Flask backend and APIs, build the frontend, work with the ML models, integrate them, fix bugs, organize the dashboard, and finally bring everything together.

While working with the ML models, I also learned several new **ML and computer-vision terminologies** because I partially trained and tested both models myself.

The project taught me that development isn't always about everything working on the first attempt. I faced problems with the YOLO model detecting only one tear, had to rethink the fabricated-image approach, had to adapt the Random Forest model to changing data, and had to fix bugs during integration.

But each problem became part of the learning process.

**The biggest takeaway from this journey is that I became confident that I can take an idea, break it into different parts, develop those parts, solve the problems that appear along the way, and finally bring everything together into a working software system.**
